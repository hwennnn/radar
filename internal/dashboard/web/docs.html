How Radar works

This page follows a job from source discovery to PostgreSQL, the public job list, and the Telegram outbox.

Contents
Pipeline Source discovery Crawl cycle Job identity Eligibility Delivery and recovery

Request path

One loop finds possible career pages. A second loop fetches jobs from pages that passed the source checks.

Source records
Candidate URLs, verified sources, check results, failure counts, and the next retry time.
Job records
Raw observations, job rows, identity aliases, source history, and filter results.
Persistence
PostgreSQL stores dedupe and retry state. Restarting the process does not clear either one.

Source discovery

A discovered URL is saved as a candidate first. Radar identifies the job platform and tests the URL with the same adapter used by scheduled crawls.

candidateA possible careers URL. Scheduled crawls do not use it yet.
validatingThe worker is checking the company, adapter, and response.
promotedThe test returned a valid job list. Scheduled crawls may now use it.
unhealthyThe request or parser failed. The next attempt runs after a stored delay.

Source checks

  • The careers route belongs to the expected company.
  • The provider has a supported structured or company-specific adapter.
  • The adapter can read the full job list, not only one search result page.
  • A non-empty response contains job titles and apply links. Known ATS APIs may also return a confirmed empty list.

HTTP 200 is not enough. An unknown page that returns no jobs stays a candidate until Radar can verify what it is.

Crawl cycle

  1. 1
    Lock the scheduler

    A PostgreSQL advisory lock allows only one routine process to start the cycle.

  2. 2
    Read scheduled sources

    The query selects promoted sources whose next attempt time has arrived.

  3. 3
    Fetch every current posting

    The source adapter returns a complete list or an error. A failure for one company does not stop the others.

  4. 4
    Write each posting

    The transaction resolves job identity, updates the job and source history, and inserts the delivery row.

  5. 5
    Mark the fetch complete

    Staged delivery rows become pending only after the whole source response has been processed.

  6. 6
    Update source status

    The worker stores the job count, error, failure count, and next attempt time.

Job identity and deduplication

A title or location can change while the job stays open. Radar therefore matches postings by source ID and apply URL before using a title-based fallback.

URL canonicalization

The canonicalizer removes fragments and known tracking parameters, sorts meaningful query values, normalizes default ports, and unifies equivalent Greenhouse board hosts. It preserves reserved path escapes and meaningful query parameters because they may distinguish requisitions.

input Aboards.greenhouse.io/acme/jobs/42?gh_jid=42&utm_source=x
input Bjob-boards.greenhouse.io/acme/jobs/42
identityurl:https://job-boards.greenhouse.io/acme/jobs/42

Concurrent writes

For each posting, Radar computes the available identity keys, sorts them, and takes PostgreSQL advisory locks in that order. If those keys already point to different job rows, the rows are merged before the update. Two workers processing the same new job therefore cannot create separate owners.

UNIQUE (job_id, channel, recipient)

The aliases, source history, job row, and delivery row use one database transaction. If one write fails, none of them are committed.

Eligibility policy

Radar stores every parsed posting with its source. The web feed and Telegram outbox include only postings that pass these checks.

Role
Software, infrastructure, data, ML, research engineering, and quantitative engineering roles.
Career timing
Internship, university graduate, new graduate, and explicit early-career evidence.
Geography
United States, Singapore, and supported remote locations after country normalization.
Hard rejects
Senior management, support, generic operations, QA-only, stale postings, and unusable apply links.

A rejected posting gets a delivery row with status suppressed. Seeing the same job again does not create another decision.

Delivery and recovery

The first complete fetch from a new source is saved without sending old jobs. New eligible jobs use these delivery statuses:

staged→pending→claimed→sent
Source request fails
Retry during the cycle. If it still fails, write a later next_attempt_at.
Fetch stops halfway
Keep new delivery rows staged. A later complete fetch can activate them.
Telegram request fails
Return the same row to pending and retry it. Do not insert another row.
Worker exits
The database lock releases and claimed delivery leases eventually expire.

The unique index prevents Radar from creating two delivery rows for the same job, channel, and recipient. One edge case remains: Telegram may accept a message while its response is lost, so retrying that timed-out request can duplicate the message in Telegram.
